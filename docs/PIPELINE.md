# 공지 초안 파이프라인 규칙집

요청 한 건이 초안이 되기까지 거치는 단계, 단계마다 쓰는 기준값, 참고 공지를 고르는 조건, 초안을 검사하고
평가하는 방법을 코드에 적힌 값 그대로 정리했습니다. 공지 검색창(`/search`) 규칙도 끝에 함께 둡니다.

## 대원칙

**과거 공지는 형식과 문체의 예시일 뿐 사실 출처가 아닙니다. 새 공지의 사실값은 사용자가 준 입력에서만 옵니다.**

그래서 참고 공지는 사실값을 가린 채 LLM에 들어가고(`<가상자산명1>(<티커1>)` `<날짜>` `<시각>` `<차수>`
`<링크>` `[조항 확인 필요]`), 초안에 나온 코인·날짜·시각·링크·조항은 코드가 입력과 한 번 더 대조합니다.

## 흐름

요청은 아래 여덟 단계를 차례로 거칩니다. LLM은 6~8단계에서만 부르며, 생성·평가·수정·재평가를 합쳐
최대 4회입니다. 2단계의 유형 추정에는 LLM이 아니라 Bedrock 임베딩(Titan V2)을 씁니다.

| 단계 | 하는 일 | 함수 | 여기서 멈추면 |
|---|---|---|---|
| 1 요청 확인 | 카테고리 1~2개, 요청문, 입력값을 받습니다. 카테고리가 0개이거나 3개 이상, 중복, 모르는 이름이면 멈춥니다. 옛 형식(`category`, `answers`, `coin_kr`·`ticker`·`datetime`)도 새 형식으로 바꿔 받습니다. | `resolve()` | `error` |
| 2 유형 판별 | 카테고리마다 유형을 하나씩 정합니다. 우선순위는 사용자 지정 → 요청문 규칙 → 비슷한 공지 5건 다수결 추정 → 일반(general). | `resolve_with_estimate()` | — |
| 3 필수값 확인 | 유형별 필수 입력이 비었는지, 값 형식이 맞는지 봅니다. 모자라도 여기서 멈추지 않고 후보 공지까지 찾아 보여 준 뒤 5단계에서 멈춥니다. | `missing_fields`, `invalid_fields` | — |
| 4 후보 모으기 | 검색어를 만들고 BM25로 최대 세 갈래에서 후보를 모읍니다. `hybrid=true`면 의미 검색 한 갈래가 더해집니다. | `build_query()`, `find_candidates()` | — |
| 5 참고 공지 선택 | 본문 100자 미만을 빼고 등급 → 순위점수 순으로 정렬해 1위를 고릅니다. 사용자가 고른 공지가 있으면 그것을 씁니다. | `rank_candidates()`, `select_reference()` | `need_input` / `ready` |
| 6 초안 작성 | 사실값을 가린 참고 공지와 입력값으로 프롬프트를 만들어 초안을 생성합니다. (LLM · gpt-4o-mini) | `build_prompt()` | — |
| 7 검사·평가 | 코드 사실 검증은 항상 돌고, LLM 평가는 `evaluate=true`일 때만 돕니다. (LLM · gpt-4o) | `check_draft()`, `evaluate()` | — |
| 8 1회 수정 | 코드 오류가 있거나 평가가 기준에 못 미치면 한 번만 고칩니다. 고친 뒤 오류가 더 많으면 1차본을 씁니다. | `build_revision_prompt()` | 끝: `ok` / `needs_review` |

| API | 도는 단계 | LLM 호출 | 쓰임 |
|---|---|---|---|
| `POST /prepare` | 1–5 | 없음 | 유형·질문·후보 확인 |
| `POST /draft` | 1–8 | 2~4회 (평가 끄면 1~2회) | 초안 생성 |
| `POST /check` | 1–3 + 7의 코드 검사 | 없음 | 사용자가 고친 초안 재검사 |
| `GET /notice` | — | 없음 | 후보 미리보기(원문 + 최초 버전 + 판별 유형) |

## 입력·옵션값

### 요청에 담는 값 (/prepare · /draft · /check 공통)

| 필드 | 뜻 | 기본값 |
|---|---|---|
| `categories` | 카테고리 1~2개. 예) `["안내","입출금"]` | 필수 |
| `subtypes` | 카테고리별 유형 직접 지정. 규칙·추정보다 우선합니다. 추정이 틀렸을 때 바로잡는 통로입니다. | 없음 |
| `text` | 요청문. 유형 판별, 검색어, general의 공지 주제로 쓰입니다. | `""` |
| `inputs` | 문답값(모든 파트 공통). `coins`·`suspend_at`·`reason` … | `{}` |
| `part_inputs` | 카테고리마다 다른 값. 예) 파트별로 대상 코인이 다를 때 | `{}` |
| `base_notice_url` | 참고 공지를 직접 지정합니다. | 자동 선택 |
| `evaluate` | LLM 평가 포함 여부. 코드 검사는 이 값과 관계없이 항상 돕니다. | `true` |
| `hybrid` | 후보 검색에 의미 검색을 섞습니다([비교 결과](#쓰지-않는-기능)). /check에서는 쓰지 않습니다. | `false` |
| `draft` / `title`+`body` | /check 전용. 검사할 초안 | — |

### 코드에서만 바꾸는 옵션 (`draft_notice`)
- `top_k` = **5** — 응답의 `candidates`에 보여 줄 후보 수
- `prepare_only` — /prepare가 true로 부릅니다(5단계에서 멈춤).

### 환경변수
| 이름 | 기본값 | 뜻 |
|---|---|---|
| `LLM_PROVIDER` | openai | local · company로 전환 |
| `OPENAI_MODEL` | gpt-4o-mini | 초안 생성 |
| `EVAL_MODEL` / `EVAL_PROVIDER` | gpt-4o / LLM_PROVIDER를 따라감 | 평가 |
| `LLM_TIMEOUT` | 90 | LLM 호출 1번 제한시간(초) |
| `LLM_MAX_RETRIES` | 1 | 일시 오류·호출 한도 재시도 횟수 |
| `NOTICE_INDEX` | notices_v3 | OpenSearch 인덱스 |
| `BEDROCK_EMBED_MODEL` | amazon.titan-embed-text-v2:0 | 임베딩(서울 리전) |

temperature 0.3은 코드에 고정입니다(생성·평가 공통).

### 입력값 표기 규칙
- **아직 모르는 값**: `미정` · `미확정` · `추후 공지` · `추후공지` · `추후 안내` · `tbd`. 필수값 검사는 통과하고, 초안에는 확정값 대신 '추후 안내'나 [확인 필요]로 씁니다.
- **일시**: `2026-09-10 19:00`을 넣으면 코드가 요일을 계산해 **2026.09.10(목) 오후 7:00(KST)** 로 바꿔 프롬프트에 넣습니다. LLM에게 요일을 계산시키지 않습니다.
- **코인**: `메가이더(MEGA)`처럼 한글명(티커) 꼴이며, 여러 개를 넣을 수 있습니다.
- **general 유형**: 요청문이 '공지 주제'로 자동으로 들어갑니다.

## 유형 판별

카테고리 안에서는 표의 위에서부터 먼저 맞는 규칙이 이깁니다(예: '지정 해제'는 '지정'보다 먼저 봅니다).
규칙은 요청문과 사유를 붙인 문장에 적용합니다. 참고 후보의 유형을 가를 때도 같은 규칙을 제목에 적용하되,
에어드랍 완료·예정처럼 제목만으로 안 갈리는 유형은 본문('지급이 완료되었습니다' / '…예정입니다')까지 봅니다.
공지 수는 실제 공지 4,237건의 제목을 분석한 값입니다.

같은 필드는 한 번만 묻습니다.

### 판별 우선순위
1. 사용자가 `subtypes`로 지정한 유형
2. 요청문 규칙(위 표의 판별 표현)
3. 비슷한 공지로 추정(아래 조건)
4. 일반(general)

### 추정 유형 — 규칙이 못 정할 때
- **조건**: 규칙 결과가 general이고, 사용자가 지정하지 않았고, 그 카테고리에 유형이 있고, 판별 문장이 **8자 이상**일 때
- **방법**: 요청문과 뜻이 가장 가까운 그 카테고리 공지 **5건**의 유형을 보고, 가장 많은 유형이 **3건 이상**이면서 general이 아니면 채택합니다.
- **표시**: `parts[].estimated=true`, `estimated_subtypes`(유형·표 수·근거 공지 5건), 경고 문구
- **실패하면**(Bedrock 오류) 경고만 남기고 general로 진행합니다.
- **근거**: 사용자 말투 요청 11개 중 규칙만으로 2개, 추정을 더하면 10개를 맞혔습니다. 기존 라벨링 질의 20/20, general로 남아야 할 질의 23/24는 그대로입니다.

## 유사 공지 고르기

검색어를 만들고, 후보를 모으고, 뺄 것을 빼고, 등급과 점수로 줄을 세워 1위를 고릅니다.

### ① 검색어
유형 대표 표현(예: '입출금 일시 중지 안내') + 사유·공지 주제·핵심 내용·개정 대상·대상 서비스·제한 대상·주요
개정 내용(각 80자까지) + 요청문을 이어 붙입니다. **이번 공지의 코인명·티커는 뺍니다.** 같은 코인의 옛 공지가
끌려오면 그 공지의 네트워크·일정이 새 공지로 새기 쉽기 때문입니다.

### ② 후보 풀 (겹치는 공지는 한 번만)
| 갈래 | 조건 | 건수 | 정렬 |
|---|---|---|---|
| 기본 | 선택한 카테고리를 **모두** 가진 공지 | 50 | 관련도, 같으면 최신 |
| 카테고리 2개일 때 | 1차(첫 번째) 카테고리를 가진 공지. 태그가 한쪽만 붙은 공지가 있어서 넣습니다. | 50 | 관련도, 같으면 최신 |
| 같은 유형 최신 | 1차 카테고리 + 제목에 유형 구절('제목 가점 구절' 첫 번째)이 있는 공지. general은 이 갈래가 없습니다. | 10 | 최신순 |
| 의미 검색 | `hybrid=true`일 때만. 선택한 카테고리를 모두 가진 공지 중 뜻이 가까운 공지이며, BM25 점수는 0으로 둡니다. | 50 | 유사도 |

BM25 설정: 제목 가중치 ×3 + 본문, 제목에 유형 구절이 있으면 가점 ×2. 분석기는 notices_v3(Nori 형태소,
소문자화, 조사·어미 제거)이고, 검색할 때만 동의어를 적용합니다(중지 = 중단 = 정지 · 에어드랍 = 에어드롭 ·
상장폐지 = 거래지원 종료).

### ③ 빼는 공지
본문이 **100자 미만**인 공지(예: 본문 없는 '재산상 이익 제공' 공시)는 참고로 쓰지 않습니다.

### ④ 등급 — 먼저 등급으로 가르고
| 등급 | 뜻 | 조건 |
|---|---|---|
| **0** | 유형 일치 | 후보의 제목(+최초 본문)으로 판별한 유형이 이번 요청의 유형과 같음 |
| **1** | 유형 일치(다른 내용이 합쳐진 공지) | 유형은 같지만 선택하지 않은 카테고리가 붙었거나, 유형 1개 요청인데 제목에 '및'이 있음 |
| **3** | 같은 카테고리지만 유형 다름 | 1차 카테고리는 있지만 유형이 다름 |
| **4** | 카테고리 불일치 | 1차 카테고리가 없음 |

### ⑤ 순위점수 — 같은 등급 안에서는 점수로
```
순위 = 등급 낮은 순 → 같은 등급이면 순위점수 높은 순

순위점수 = a × 관련도 + b × 최신성
  유형 있는 요청   a 0.5 · b 0.5   양식이 같아서 최신 문구가 중요
  general 요청    a 0.8 · b 0.2   주제가 제각각이라 내용 관련도가 중요

관련도 = BM25 점수 ÷ 후보 중 최고 점수              (0~1)
       하이브리드면 0.5 × BM25 + 0.5 × 의미 유사도(후보 안 최소~최대를 0~1로)
최신성 = 1 − 게시 후 경과일 ÷ 1,095              (3년 지나면 0)
```
Titan 코사인 유사도는 0.3~0.6에 몰려 있어서, 그대로 섞으면 차이가 나지 않아 후보 안에서 0~1로 폅니다.

### ⑥ 선택
- 1위를 자동으로 고르고, 응답에는 상위 5건을 보여 줍니다.
- 1위가 등급 3 이상이면 선택 이유에 '형식 신뢰도 낮음'이 붙습니다.
- `base_notice_url`을 주면 그 공지를 씁니다. 등급 3 이상이면 경고를 띄우고, 찾을 수 없으면 error입니다.
- 후보가 하나도 없으면 일반 형식(인사말 → 안내 → 항목 → 유의사항 → 끝인사)으로 씁니다.

### ⑦ 최신 문체 참고 1건
- 선택한 공지보다 최신인 같은 등급 공지 중 가장 최신 1건
- 본문 앞 700자를 가려서 넣고, 인사말·끝인사·호칭 표현만 참고시킵니다.

### ⑧ 업데이트된 공지는 최초 버전으로
- **제목**: 끝의 괄호 꼬리표를 뗍니다. 괄호 안에 재개·연기·완료·정상화·종료·업데이트·취소·변경·추가가 있거나, 날짜와 함께 지급·출금이 있으면 꼬리표로 봅니다. 예) 디와이디엑스(DYDX) 입출금 일시 중지 안내 ~~(09/12 재개)~~
- **본문**: 마지막 '안녕하세요'부터를 원문으로 보고, 그 위에 덧붙은 재개 안내를 뺍니다. 남는 원문이 100자 이상일 때만 자릅니다.
- 새 초안은 최초 공지이므로 재개 내용은 쓰지 않습니다. 무엇을 뺐는지는 `selected_reference.update_removed`에 남습니다.

## 검사·평가

초안은 코드와 LLM이 서로 다른 것을 봅니다.

| | 코드 사실 검증 (`factcheck`) | LLM 평가 (`evaluator`) |
|---|---|---|
| 언제 | 항상 (/draft, /check) | `evaluate=true`일 때 (/draft만) |
| 무엇 | 사실값: 입력과 어긋난 코인·날짜·시각·링크·조항, 복사한 문장 | 의미·문체·완결성: 형식, 어투, 유의사항, 지어낸 내용 |
| 비용·속도 | 없음 · 즉시 | gpt-4o 1회 (수정하면 1회 더) |
| 결과 | 오류/경고 목록 → 최종 상태(ok/needs_review)를 정함 | 5개 기준 점수 → 수정 여부에만 쓰임 |

### 코드 사실 검증 항목
| 코드 | 심각도 | 잡는 것 |
|---|---|---|
| `format` | 오류 | '제목:'/'본문:' 형식이 없거나 본문이 비었음 |
| `missing_value` | 오류 | 사용자가 준 값(코인명·티커·일시·링크·네트워크·서비스명 같은 고유명)이 초안에 없음. 필수든 선택이든 적용 |
| `foreign_coin` | 오류/경고 | 참고 공지의 코인이 섞이면 오류, 입력에 없는 티커·약어는 경고 |
| `unknown_date` | 오류 | 입력에 없는 날짜 |
| `weekday` | 오류 | 틀린 요일 |
| `unknown_time` | 오류 | 입력에 없는 시각 |
| `resume_date` | 오류 | 재개 일시를 안 줬는데 제목에 '(MM/DD 재개)'가 있거나, 입력과 다른 재개 날짜가 있음 |
| `label_value` | 오류 | '대상 네트워크: …', '지정일: …' 같은 라벨 줄에 입력하지 않은 값이 채워졌거나, 입력과 다른 날짜가 들어감 |
| `unknown_url` | 오류 | 입력에 없는 링크 |
| `law_clause` | 오류/경고 | 입력에 없는 조항 번호는 오류. 조항이 있으면 항상 '사유에 맞는지 검증 필요' 경고 |
| `unknown_number` | 오류 | 입력에 없는 심사필 번호 |
| `placeholder` | 오류 | `<…>` 자리표시자가 남음([확인 필요]는 허용) |
| `section` | 경고 | 유형별 필수 항목이 안 보임(표현이 다양해서 경고만) |
| `guard` | 오류 | 입력하지 않은 사실의 금지 서술. 예) 재개 일시 없이 '재개합니다', 입금 제한 없이 '입금이 중단된 상태' |
| `role` | 오류 | 코인 역할이 뒤바뀜. 에어드랍 '(티커) 보유자' 자리는 보유 기준 가상자산이어야 합니다. 틀린 문장과 정답을 함께 알려 줍니다. |
| `reference_copy` | 오류/경고 | 참고 공지에만 있는 문장을 그대로 옮김. 2줄 이상이면 오류, 1줄이면 경고(/check에서는 보지 않음) |

복사 판정: 참고 공지의 30자 이상 줄 가운데, 같은 등급의 다른 후보 최대 8건에 80% 이상 비슷한 줄이 없으면
'그 공지 고유 문장'으로 봅니다. 초안 줄이 고유 문장과 90% 이상 비슷하면 복사입니다. 인사말·유의사항처럼 여러
공지에 반복되는 고정 문구는 복사로 보지 않습니다. 초안의 [확인 필요]류 표시와 [확인 필요 사항] 목록은
`needs_confirmation`으로 모읍니다.

### LLM 평가 기준 (각 1~5점, 합계 25점)
| 기준 | 보는 것 | |
|---|---|---|
| `format` | 형식 준수: 공지다운 항목 구성과 필수 항목을 갖췄는가 | |
| `tone` | 최신 어투: 인사말·끝인사·회원 호칭이 참고 공지의 최신 스타일과 일관적인가 | |
| `caution_fit` | 사유-유의사항 일치·완결성: 유의사항과 안내가 이번 사유·유형에 맞고 빠진 것이 없는가 | |
| `no_fabrication` | 지어내지 않음: 요청에 없는 사실(상태·일정·수치·기관)을 채우거나 덧붙이지 않았는가 | 핵심 |
| `fixed_values` | 입력값 충실도: 코인·티커·날짜·대상이 정확히 반영됐는가 | 핵심 |

- **평가기에 주는 것**: 공지 유형, 요청 정보(파트별로 나눔), 코드가 계산한 요일 정답, 필수 항목, 코드 검증 결과, 가린 참고 공지 발췌 600자, 초안
- **감점하지 않는 것**: [확인 필요]·[조항 확인 필요]·[네트워크 확인 필요] 표시, 파트마다 다른 값
- 종합 판정은 통과 / 검토필요 / 실패입니다. 평가 자체가 실패하면(응답 형식 오류, 호출 실패 등) '평가불가'가 되고, 평가를 근거로 한 수정은 하지 않습니다.

## 1회 수정

아래 조건 중 하나라도 해당하면 딱 한 번 고칩니다.

- 코드 검사 **오류 1개 이상**
- 평가 판정 **실패**
- 평가 합계 **18점 미만** / 25
- no_fabrication · fixed_values 중 **3점 미만**

**수정 프롬프트에 넘기는 것**
- 원래 프롬프트 + 1차 초안
- 반드시 고칠 문제: 코드 오류 메시지, 3점 이하 기준의 평가 코멘트, 필수 항목 경고
- 지시: 지적된 부분만 최소로 고치고, 입력에 없는 값은 지우거나 [확인 필요]로 바꿉니다. 문제에 인용된 문장은 반드시 그 문장을 고칩니다.

**수정본 채택 규칙**
- 수정본의 코드 오류가 1차본보다 **많으면** 1차본을 최종본으로 유지하고 경고를 남깁니다.
- 같거나 적으면 수정본을 채택하고, 수정본을 다시 평가합니다.
- **수정 호출 자체가 실패하면**(GPT 오류·제한시간 초과) 이미 만든 1차본을 최종본으로 돌려주고 경고를 남깁니다.
- 두 번째 수정은 없습니다(`MAX_REVISIONS = 1`).

## 결과 상태와 오류 응답

응답의 `status` 값별로 다음에 할 일이 정해집니다.

| status | 언제 | 다음 할 일 |
|---|---|---|
| `error` | 카테고리 개수·이름 오류, 없는 유형 지정, 지정한 참고 공지를 못 찾음 | 요청을 고쳐 다시 보냄 |
| `need_input` | 필수값이 비었거나 형식이 틀림. 후보와 자동 선택은 함께 옵니다. | `missing_fields`의 질문에 답해 다시 보냄 |
| `ready` | /prepare에서 준비 완료 | 같은 값으로 /draft 호출(참고 공지를 바꾸려면 `base_notice_url`) |
| `ok` | 최종본에 코드 오류 없음 | [확인 필요] 항목을 채워 검토·게시 |
| `needs_review` | 최종본에 코드 오류가 남음 | `final_check.issues`를 보고 고친 뒤 /check |

주요 응답 필드: `parts`(estimated 표시 포함) · `estimated_subtypes` · `missing_fields` · `candidates`(상위 5건:
tier·relevance·recency·rank_score) · `selected_reference`(+original_title·update_removed) · `selection_reason` ·
`first_draft`/`first_check`/`first_evaluation` · `revision_attempted`/`revision_reasons`/`revised` ·
`final_draft`/`final_check`/`final_evaluation` · `needs_confirmation` · `warnings`

### 외부 서비스가 실패할 때 (HTTP 오류)
본문은 `{"detail": 안내 문구, "kind": 종류}`입니다. 이 응답에는 CORS 헤더가 붙어 브라우저가 이유를 읽을 수 있습니다.

| 상황 | HTTP | kind |
|---|---|---|
| GPT 호출 실패·호출 한도 초과·API 키 오류 | 502 | `error` · `rate_limit` · `auth` |
| GPT 응답 제한시간(90초) 초과 | 504 | `timeout` |
| LLM 설정 없음(키·provider) | 503 | `config` |
| 검색 서버(OpenSearch) 연결 실패 | 503 | `search_unavailable` |
| 필수 환경변수 없음 | 503 | `config` |
| 없는 공지(`/notice`) | 404 | — |
| 검색 쪽 번호가 너무 큼(`page × size` > 10,000) | 422 | — |

실패해도 멈추지 않는 것: LLM 평가 실패(→ '평가불가'), 수정 호출 실패(→ 1차본 유지), 유형 추정·의미 검색 실패(→ 경고
후 규칙·BM25만), /prepare 중 검색 실패(→ 경고).

## 검색창 /search

공지를 찾는 검색창용 API입니다(`search.search_page`). 초안 흐름의 후보 검색과는 따로 동작합니다.

| 항목 | 규칙 |
|---|---|
| 본 목록 | BM25(제목 ×3 + 본문). **1위 점수의 50% 미만은 뺍니다.** 사전에 없는 이름('헤데라')은 형태소 조각('헤'+'데')으로 쪼개지고, 기본 검색은 조각 하나만 맞아도 결과에 넣어 긴 꼬리가 붙었습니다(헤데라 78→14건, 메가이더 4,229→4건). |
| 정렬 | `relevance`(관련도순, 같으면 최신) / `recent`(최신순) |
| 카테고리 | `category`로 거릅니다. 50% 기준(1위 점수)은 카테고리와 무관하게 전체에서 잡고, 카테고리는 `post_filter`로 겁니다. 그래서 `categories`(카테고리별 건수)가 그 카테고리를 눌렀을 때의 결과 수와 같습니다. |
| 쪽 나눔 | `page`·`size`(1~50). 앞쪽 10,000건까지만 볼 수 있습니다(넘으면 422). |
| 발췌 | `snippet`은 HTML 이스케이프한 본문 발췌이며 `<em>`만 들어 있습니다. 검색어가 본문에 없으면 본문 앞부분입니다. |
| 비슷한 공지 `related` | 1쪽에만, 1쪽에 안 보이는 공지 중 뜻이 가까운 것 **5건**(의미 검색). 검색어가 **두 단어 이상이거나 결과가 0건일 때만** 붙입니다. 한 단어 코인명에 붙이면 다른 코인 공지만 끌려왔습니다. Bedrock이 실패하면 빈 목록입니다. |

벡터 결과를 본 목록에 섞지 않은 이유: kNN은 항상 k건을 돌려주고, 정답과 오답의 유사도 분포가 겹쳐 결과
건수를 정할 기준이 되지 못합니다(코인명 정답 0.2~0.3, 오답 최고 0.15~0.36).

실측(제목 정규식을 정답으로 사용): 코인명 15개의 결과 수가 평균 734건에서 25건으로 줄었고 정확도 93%·재현율
98%입니다. 첫 화면 정답 수는 general 문장형 1.4 → 3.2, 동의어 8.2 → 11.8입니다. `GET /ui`는 이 API를 쓰는
간단한 검색 화면입니다.

## 쓰지 않는 기능

코드에는 있지만 기본 흐름에서 쓰지 않는 것들입니다.

- **하이브리드 후보 검색**: 요청의 `hybrid=true`로만 켭니다. 비교해 보니 유형이 정해진 요청에서는 BM25와 결과가 같고, general을 풀어 쓴 문장에서만 1위 적중이 33%에서 42%로 올라 기본값은 끔으로 두었습니다.
- **리랭커 · HyDE**: `search.hybrid_search()`(CLI `search --hybrid --rerank`)에만 남아 있고, API와 초안 흐름 어디에서도 쓰지 않습니다.
- **/check의 복사 검사**: /check는 참고 공지 고유 문장 복사를 보지 않습니다. `base_notice_url`을 주면 코인 혼입만 봅니다.
- **맞춤법 검사**: 아직 없습니다(이슈 #5).
